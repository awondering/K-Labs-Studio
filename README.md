## Build sync transition (development only)

The candidate client uses temporary compatibility mode only when the guard-version RPC is absent. Its revision checks are not protection against v208 writes: use one approved device at a time and pause all other writers. Guard protocol 2 requires revision checks for updates and deletes and a marker for inserts; v208 cannot write protected builds after activation. Pending changes and conflict archives are account-scoped on the device.

Do not deploy the draft guard independently. The [controlled release and recovery procedure](./SYNCHRONISATION-RELEASE.md) requires preserving legacy sessions **before deploying the client**: v208's service-worker update can automatically reload an open session. An offline or unidentified v208 session cannot be forced to update, can show Saved after a rejected cloud write, and can lose its in-memory deletion queue. Stop if its recoverable changes and deletion intentions cannot be accounted for; no automated test removes that limitation.

Settings → Local Data Recovery → **Export Studio Data** downloads an unencrypted JSON copy of the signed-in account's local business keys, sync journal, and current in-memory draft, plus separately labelled shared and signed-out data. Customers are included in build records. Other accounts' scoped data and authentication tokens are excluded. Shared data is not evidence of ownership. Store the file securely; it does not contain cloud-only records, uncommitted form input, IndexedDB, service-worker data, or lost v208 in-memory deletion intentions. A download request is not proof the file was saved; verify it in Files or Downloads. The export only exists in versions containing this feature: an already-running v208 session cannot use it without upgrading, and must not be refreshed or reconnected merely to obtain it.

## Payments and customer invoices

Payment Status separates the configured deposit from payments received. Deposit and balance payments, and corrections with a reason, require an online server acknowledgement on a saved, synchronised build. If the connection fails during a request, use **Confirm Pending Transaction** on that build before trying another transaction; retries reuse the same operation ID. If sync has already loaded the acknowledged result, retrying it does not create a false conflict; subsequent concurrent changes still require review.

Customer Invoice previews the current build before issuance. Issuing it online stores an immutable customer-facing snapshot with a number derived from the account and full build ID. New snapshots include the recorded rod identity, finished length, explicitly labelled line/lure ratings and major fitted components where available; existing snapshots retain their original descriptions. Reprinting uses the original snapshot; **Payment Statement** shows later payments separately. The preview fits an A4 page to the available visual viewport, with page navigation and an actual-size option; printing and PDF use the original full-size document. An unissued preview may be printed or saved as a PDF marked **DRAFT — NOT ISSUED**, without an invoice number or issue date. Printing is refused if the preview's draft or issued status is inconsistent. Builds with issued invoices cannot be deleted. Customer documents contain no internal costs or margins. Optional synthetic checks are `PLAYWRIGHT_MODULE=/path/to/playwright node tests/invoice-document-browser.cjs`, `PLAYWRIGHT_MODULE=/path/to/playwright node tests/invoice-preview-browser.cjs`, and `PLAYWRIGHT_MODULE=/path/to/playwright node tests/invoice-client-browser.cjs`. Set `INVOICE_BROWSER=webkit` for Safari-engine preview tests.

The client requires `supabase/migrations/20261111000000_financial_safeguards.sql` before these operations can work. It also prevents older clients from changing payments, and an older client may misleadingly show a local save. Before any release, pause older clients, back up and test the migration, deploy the migration and matching client as a controlled change, and verify with disposable records. Do not apply it to production without separate approval. An account's pending operation and correction audit entries must be included in backup and recovery procedures.

### Financial release and protective rollback

The approved synchronisation backup and release procedure applies, but its earlier v208-specific deployment steps are historical: production already has the v211 revision guard. For a financial release, pause all writers and older clients; take a fresh encrypted native database and globals backup, verify a separate off-machine copy and an isolated restore; verify the target, guard, RLS and absence of conflicting financial objects. With explicit production approval, enable and verify the existing Kevin/Sales build freeze; apply the financial migration; verify the guard and financial triggers, RLS, ledger and RPC privileges; then publish the reviewed client and verify its served assets. The originally approved client `4f89531` (`build148-v212`) needs the subsequent lost-acknowledgement retry fix (`build148-v213`) before the financial release can proceed. Keep writers paused until guarded payments, duplicate and conflict handling, issuance, invoice preservation and isolation pass using authorised synthetic data in the unfrozen test account. Issued invoices cannot be deleted: retain any synthetic invoiced build clearly marked as a test; do not remove its ledger or customer records. Check the financial safeguards and guard again, then remove the freeze with the existing guarded disable transaction, verify both accounts using authorised disposable non-invoiced records, and resume only upgraded clients after verification. Do not automatically restore historical records.

If a release incident requires stopping financial operations, pause writers, preserve pending local operation journals and take a fresh verified backup including the ledger. Only with separate approval, run [the protective financial rollback](./SUPABASE-FINANCIAL-ROLLBACK-DRAFT.sql). It locks both tables, checks the exact deployed guard and financial functions and triggers, revokes financial RPC access, retains all data and the revision guard, and installs read-only safeguards on financial fields and the ledger. It also blocks deletion of builds with payments, issued invoices or ledger history and blocks build truncation. Administrators who can disable triggers, change privileges or alter schema can bypass these safeguards; do not do so as part of rollback. Verify the transaction and unchanged records before allowing guarded non-financial work. New financial operations and pending-operation retries remain unavailable until a separately reviewed re-enablement; do not rerun the financial migration, drop the ledger, restore an old database over newer data, or invoke the older guard-removal rollback. Publishing an older client is not a substitute for this protection and requires separate review and approval.

## Shared UI Rules

- Track Component Stock shares the Measurement Units and Date Format disclosure spacing and uses the summary "Track quantities as parts are used." Its heading target extends into the existing padding without adding visible space; descriptions wrap naturally and switch behavior is unchanged.
- Settings Pricing & Tax uses three compact label/control rows: Default tax, Tax rate (%) and Labour rate ($/hr). Numeric controls share a right edge and width; the default-tax switch omits visual OFF/ON text while retaining its accessible label and checked state. Controls retain 44px targets, decimal keypad hints and visible keyboard focus.
- The build editor's Components heading is a full-width disclosure with count and trailing chevron. Add Component sits above the existing list inside the expanded body, not in the heading or a separate card; collapsing hides it without rebuilding editors or discarding unsaved values. The heading and Add action retain native button keyboard activation, visible focus and at least 44px targets.
- Build Pricing keeps Labour Rate / Hour and Labour Hours, a three-column Freight / Packaging / Total delivery group, Components Cost, Customer Price, Required Profit and Margin %. Delivery inputs represent cost; applicable tax is included in Customer Price so post-tax delivery recovery equals its cost. Direct Total entry clears the breakdown. Legacy freight cost / charge pairs stay stored and active until a new delivery field is edited; the expandable warning shows both saved values. Existing freight component rows are preserved. Estimated Earnings is customer revenue excluding applicable tax, less component buy costs and delivery costs, without deducting labour as wages. Required Profit remains net profit above component buy cost plus the labour charge; Margin % remains true rod selling margin (profit divided by rod selling price) on that same basis. The active pricing input uses restrained red emphasis; pricing and delivery inputs retain 44px touch targets.
- Deposit type switches convert the required amount independently of recorded payments. Requirements must be between 0 and 100% or between zero and the customer price; an invalid saved value is preserved and shown for correction, and build autosave is blocked until it is corrected. Balance owing uses payments actually received.
- Every app dropdown, including selects and datalist suggestions, uses `initializeStudioCustomSelects()` in `js/ui.js`; do not expose native OS menus. Preserve the underlying value and dispatch its normal `input`/`change` events so dependent options and existing handlers continue working.
- Custom pickers reuse the dark `.component-sheet` surface, accessible labels, arrow/Home/End/Enter navigation, Escape, Cancel/outside dismissal, and focus restoration. Long lists scroll inside the visual viewport-safe sheet above navigation and safe areas; datalist inputs retain free-text entry.
- Picker triggers, option rows, and actions have at least 44px touch targets. Use compact aligned carbon controls, titanium text/fine borders, restrained red selected/focus states, and shared action styles instead of one-off picker skins.
- Individual component duplication preserves the source Category/Subcategory, Brand, pricing and sizes, and never infers or creates hierarchy from a component name. Copies receive fresh IDs and zero stock without changing stock-tracking settings. Unassigned sources remain unassigned. Duplicate Family creates a sibling family under the same category. Preserve the original and historical builds.
- Inside a saved family, Duplicate Family copies the complete family to a new sibling under the displayed parent category and returns to its A-Z family list. The dialog resolves the source by category/family IDs at confirmation; individual actions are labelled Duplicate Component.
- Build rows use `libraryComponentId` for identity, deduplication, and size resolution; use name matching only as a legacy fallback for unlinked rows.
- One-off account data repairs require a unique exact name or stronger identity, preserve unrelated fields/history/taxonomy, and skip ambiguous matches.
- Components browse as Category -> Subcategory/Family -> Components. Winding Checks colours/types are explicit families; Reel Seats may use brand-named families. Family rows show only the name and actions; Brand remains optional component data.
- Categories, families and components use the shared case-insensitive, natural A-Z display helpers after Add/Rename/Duplicate and on reopen. Stored array order and IDs are preserved; category/family Move Up/Down controls are not offered.
- Records with no Subcategory (including duplicates of unassigned components) appear inside the virtual Unassigned family bucket, not as family rows or direct category-level components. Adding a component in that bucket retains an empty Subcategory; adding a family creates taxonomy only. Names never imply record type or trigger conversion/merging. The virtual bucket has no taxonomy actions.
- Existing records such as Black Silver, Gunmetal Hexy Duplicate and Hex need a separate identity-based review if they were intended as families or assigned to one. Their names alone do not establish that intent; do not repair live data from labels.
- Focused hierarchy regression checks: `node --test tests/components-hierarchy.test.cjs`. These evaluate only the relevant UI functions with in-memory records, taxonomy and DOM doubles; they do not launch a browser, app startup, migrations, local storage or cloud sync.
- Available Sizes keeps saved chips visible. Manual entry and From/To/Step range controls sit inside a collapsed Add or Edit Sizes disclosure; editing remains draft-only until Save Changes.
- Workshop Diameter & Circumference retains live conversion and adds wraps (default 1.00, quarter-turn buttons, minimum 0.25). Wrap Length Required is circumference times wraps for straight blanks and thin sheets; it does not include thickness correction or Grip Wrap calculations.
- Guide Setup uses view-only Spacing -> Orientation -> Placement stages with explicit Continue and collapsed-stage reopening. Each collapsed heading and summary is one native button with a far-right chevron, keyboard activation, visible focus and a 44px minimum target; open headings and input bodies do not toggle stages. Reopening uses the existing Edit/scroll path. Existing controls, geometry, saved-build specification and print output remain authoritative. Guide-row angles are applied rotations from the reel side (0 degrees); focused rotation inputs retain the user's edit while limits apply (stripper 0–25, others 0–180). Surface distance uses each guide's diameter and applied reel-side angle. Per-guide diameters remain in memory; the existing build specification does not persist diameters.
- Show Offsets sits beside Show Spacing in the Guides header. Eligible non-reference guides reveal diameter and offset together without opening rotation editors. Missing/invalid diameters show "Enter blank diameter"; hiding offsets retains each guide's entered diameter.
- Guide Setup's Continue and Edit actions scroll the newly opened stage's heading to the top of the usable viewport, below the fixed header and safe-area inset, once the previous stage has collapsed and the new stage's layout has settled. Ordinary field edits and result re-renders never trigger this scroll.
- Customer History's inner Customers control returns to the customer list; the list's Studio control exits to the Studio landing view. The outer close control returns to the overlay's recorded screen/view and restores focus and scroll through the shared modal cleanup. These navigation-only exits retain the active build and unsaved edits without saving or discarding them.
- Workshop Thread Wrap Designer (`js/thread-wrap.js`, pure calculation/preview/instruction engine; UI wiring in `js/ui.js`) lays out a diamond cross-wrap on a straight-tapered blank from the wrap length and the butt-side and tip-side diameters, in the user's measurement units (marking tables always show decimal inches). Rows of crossing points are placed so every row covers equal blank surface area, the equal-area principle used by published taper-offset-spacing methods (B.D. Ehler and John Sturm, Rod Guild; Rodhouse). The helix angle is a result, not an input; angles outside 15–75° are refused. Two opposite axes follow published examples; 4 and 6 axes are an unvalidated extension. Everything is approximate and needs checking on a spare blank section. Published as a labelled Beta: the geometry and instructions have not yet been physically validated. Nothing is saved to builds, customers, pricing or Supabase. Focused checks: `node --test tests/thread-wrap-engine.test.cjs tests/thread-wrap-ui.test.cjs`.
- Workshop Guide Train Designer (`js/guide-train.js`, pure geometry/side-view engine; UI wiring in `js/ui.js`) is a separate tool, independent of Guide Spacing. From the rod, reel, spool, reel-axis, ring-ID and guide-height measurements it proposes a stripper, a reduction train and a geometric choke position using an original model documented at the top of the engine (an assumed line-flare cone, straight line segments between ring centres, and the ring-fit rule `required ID = envelope x (1 + clearance) + 2 x offset`). The flare angle, settled-line diameter and clearance are editable assumptions, not industry values; no manufacturer tables are used and no casting performance is claimed. Guide positions can be dragged or edited; geometry is millimetre-based internally. Phase 2 adds running guides between the choke guide and the tip-top: an adjustable geometric gap progression (ratio and minimum gap; the last runner is never closer to the tip-top than the minimum) that is a provisional starting point only, to be checked against blank deflection and a static-load test. Guide geometry keeps three measurements apart: ring inner diameter, ring centre height above the blank surface (the ring centre sits at blank radius + that height, so it follows the taper) and mounting position. Guides without measurements are labelled Illustrative Geometry (proposals, not specifications); a measured ring size or centre height is a fixed constraint and the guide is repositioned around it, with a warning (never an invented height) when no position works. A small session-only guide set of the builder's own measured guides can be chosen per guide; there is no guide catalogue or manufacturer data. Development branch prototype. Nothing is saved to builds, customers, pricing or Supabase. Focused checks: `node --test tests/guide-train-*.test.cjs`.
