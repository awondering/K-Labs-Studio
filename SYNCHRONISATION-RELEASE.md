# Controlled build synchronisation release

This is a release procedure, not authorisation to deploy. The server guard is a draft and production remains on v208. The client and guard must be reviewed and approved together; never apply the guard as a standalone change.

## Temporary production build freeze

The draft [enable script](./SUPABASE-BUILD-FREEZE-ENABLE-DRAFT.sql) blocks inserts, updates and deletes to the two specified account IDs and rejects `TRUNCATE` for the whole builds table. It also blocks the guarded delete RPC because that function's delete fires the same row trigger. It does not freeze components, settings or other tables, and an administrator able to disable triggers or change the schema can bypass it. Verify the IDs still correspond to the intended accounts before use. Enabling takes a table lock and waits for existing writes; verify that both enabled triggers exist after commit.

The draft [disable script](./SUPABASE-BUILD-FREEZE-DISABLE-DRAFT.sql) refuses to remove the freeze unless guard version 2, both enabled guard triggers and the guarded delete RPC exist. This presence check is not a substitute for functional verification. Test freeze and guard behavior in isolation before production. An old v208 client can display Saved even if its write was rejected, or if an RLS-filtered operation affected zero rows: never use the freeze as a client-visible warning. Stop and keep old clients from attempting cloud writes; preserve pending data or explicitly accept its loss before any refresh.

The revision guard protects the entire builds table, not just these two accounts. The freeze does not protect other accounts before the guard is active. Account for all affected users and legacy sessions, and pause their writes during the transition; do not assume everyone has upgraded.

## Before any release

1. Stop cloud writes on all accounts and inventory every browser, installed web app, device, tab and account that may have run Studio v208. An offline or forgotten session is still a potential writer. Do not refresh, sign out, switch accounts, close tabs, clear site data, reconnect an offline device or deploy a new service worker before preserving that session.
2. Obtain a fresh consistent production database backup including schema, policies, functions and business tables. Encrypt it, verify integrity, confirm a separate off-machine copy, and test restoration in an isolated project. Preserve existing backups unchanged. Record the deployed v208 commit, hosting configuration and schema definitions needed for rollback. Stop on any backup or restore verification failure.
3. On each inventoried legacy device, preserve a read-only copy of its Studio website storage and identify the signed-in account. Include the account-scoped `klabs-workshop-builds:<account-id>`, `klabs-workshop-quotes:<account-id>`, `klabs-workshop-quote-current:<account-id>`, `klabs-workshop-component-library:<account-id>`, `klabs-workshop-component-taxonomy:<account-id>`, account settings and business profile, and any unsuffixed legacy keys. Capture IndexedDB and service-worker storage as well, without exporting authentication tokens or credentials. Store the copy encrypted; verify it is complete and accessible before proceeding. Do not assign unsuffixed data to an account without separate evidence.
4. Compare the preserved builds and draft against a fresh read-only cloud snapshot by **unique build ID**, not build number. Review components, payments, invoice data, settings and customer links. Preserve both sides of any discrepancy and record the account and device. An operator must explicitly recover approved local-only changes before any refresh; do not blindly import or overwrite records.
5. Ask the user to identify every intended deletion from each session and compare it with the cloud and preserved local records. The v208 deletion queue is an in-memory `Set`, not a durable journal. A pending deletion cannot be reconstructed reliably from a storage backup or a missing local build; an interrupted or forgotten deletion requires manual investigation and explicit user reconciliation. If a session is inaccessible, lost, unaccounted for, or has an uncertain deletion, recovery cannot be guaranteed: stop the release rather than infer an answer.
6. Only after each device is preserved and reviewed, close its legacy tabs while disconnected. Keep any unreviewed offline device disconnected. Specifically account for v208's automatic service-worker activation and controller-change reload: publishing a client can refresh an already-running online v208 tab without asking. Do not rely on the candidate client to prevent that old-client behavior.

## Release after separate approval

1. In a separate environment, rerun the complete suite and both PGlite integration scripts. Test with synthetic accounts, including desktop and the actual iPhone Safari/PWA: open two tabs for one account (the second must be blocked), save/edit/delete, disconnect and restart, reconnect, exercise a two-device conflict, review and resolve it, and switch between two accounts. Check that cloud confirmation, warnings and retained journals agree with the database. Do not use customer records for the test. Stop on any mismatch.
2. With the writer pause in place, take and verify a fresh complete production backup, an off-machine copy and an isolated restore. Verify the target IDs, schema, RLS, policies and any existing trigger names. With separate production approval, execute the exact freeze-enable transaction and verify both freeze triggers. Its protection only covers build writes for the two specified accounts.
3. Publish the reviewed client at `bb31d9a` and its `build148-v211` service-worker cache. Verify served assets. Do not try normal saves or deletes for the frozen accounts: the freeze must reject them. Before guard activation, compatibility mode does **not** prevent an old client from overwriting an unfrozen account. Continue pausing all ordinary writes. Compatibility tests may use an authorised disposable third account, never customer data.
4. With the freeze and writer pause maintained, recheck the fresh backup and read-only preflight. Apply the exact reviewed `SUPABASE-BUILD-WRITE-GUARD-DRAFT.sql` transaction only with explicit production approval. Confirm the transaction completed, guard version RPC returns `2`, expected triggers and delete RPC exist, and RLS still isolates accounts. If schema or permissions differ from the isolated test, stop.
5. On disposable records in an authorised unfrozen test account, verify guarded create, update and delete, stale-write rejection, conflict review, rejection of old-client writes and account isolation. Confirm frozen-account writes still fail and no client falsely indicates cloud confirmation. Verify business records and payment totals against the preflight snapshot.
6. Only after these checks and confirmation that v208 sessions cannot attempt cloud writes, execute the freeze-disable transaction. Verify freeze triggers are gone while guard triggers and RPC remain. Using upgraded clients and disposable records, verify both accounts can save, delete and recover conflicts. Keep ordinary writes paused if any check fails. Any later-discovered legacy session must not synchronise until its owner has accepted or preserved local changes and upgraded.

The synthetic third account in the isolated integration tests is not a production
login. Creating an unfrozen production test account and its write entitlement
requires separate approval; do not use Kevin's or Sales' customer records for
testing. Pause and preserve all other writers even when using that account.

## Rollback and incidents

If client verification fails before guard activation, keep the writer freeze, preserve the affected device journals and local storage, and restore the recorded v208 hosting artifacts only after legacy recovery. Do not silently resume multi-device writes: v208 has no server conflict protection.

After guard activation, **do not restore v208 while the guard is active**: its writes are rejected and it can falsely report Saved. If the guarded client fails, keep writes stopped, preserve all device journals/conflict archives and the current database, and repair or redeploy a compatible guarded client. The [rollback draft](./SUPABASE-BUILD-WRITE-GUARD-ROLLBACK-DRAFT.sql) targets only the verified pre-release baseline with no prior guard functions or user triggers. It requires the exact guard and freeze bodies and triggers, takes a table lock, fails closed on drift, and leaves the freeze in place. It does not roll back customer rows. Before using it, separately approve the rollback, freeze all writers, verify a fresh backup and confirm that the baseline and privileges remain unchanged. Afterward verify policies and data before any client rollback. The standard freeze-disable script refuses to remove the freeze without the guard; a separate reviewed and approved recovery procedure is required to remove it after rollback.

The candidate client records `guardSeen` and deliberately refuses automatic downgrade; preserve its pending data and use a separately reviewed recovery procedure rather than clearing that marker or journal. Removing the guard removes concurrency protection. Never restore a database backup over newer data without an explicit, reviewed recovery decision.
